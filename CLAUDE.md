# Kongo

A web page that shows live stats for a Linux server, in the style of Windows Task Manager. It has six meters (CPU, Memory, Disk Read, Disk Write, Network In, Network Out), each with a 60 s history graph and the current value, plus panels for the system, filesystems and network by container, and a sortable process list. It runs as one Docker container on port **8090**.

## Working environment

- **The repo is public.** Details about the user's own server (host name, paths, users, hardware, the services it runs, how to reach it) belong in `CLAUDE.local.md`, which is not committed. Never put them in tracked files, comments or commit messages. Use generic examples instead.
- Local settings such as `TZ` go in `.env` next to `docker-compose.yml`, which is not committed either.

## Architecture

- `app/main.py` is FastAPI + psutil. A `Sampler` loop samples once a second. It computes rates from counter deltas and keeps a 60-point history in a `deque`. It pushes JSON to every client over the WebSocket `/ws`: an `init` message with the history on connect, then a `tick` message each second. `GET /api/snapshot` is for debugging and takes about 2 s, because it waits for two ticks so that the process CPU and IO deltas are valid.
- `app/static/` has `index.html`, `style.css` and `app.js`, with no external dependencies. The graphs are drawn by hand on `<canvas>` (the `Chart` class in `app.js`). The process table re-renders `tbody` on every tick. Sorting, filtering and the selected row are kept in the `table` object.
- `docker-compose.yml` runs the container with `network_mode: host` and `pid: host`, so it sees the real NIC counters and every host process. It adds `cap_add: SYS_PTRACE` and `apparmor:unconfined` so it can read `/proc/<pid>/io`, and it mounts `/etc/passwd` and `/etc/group` read-only to resolve user names. It also mounts `/var/lib/docker/containers` read-only to look up container names.

## Decisions and gotchas

- **Disk:** only whole disks are summed (`DISK_RE`: `sdX`, `nvmeXnY`, …). Partitions and loop devices would double count.
- **Network:** only physical NICs are counted, meaning those with `/sys/class/net/<if>/device`. Docker bridges and veth interfaces would double count. The env var `NET_IFACES` overrides this.
- **CPU:** psutil does not count iowait as busy, which matches Task Manager. On servers with busy HDDs iowait can be high, so `top` shows a lot of `wa` that is not part of the CPU value. A process's CPU % is normalized against all cores, so the processes add up to the total.
- Processes are only collected while a client is connected (`with_procs`). This costs about 2 % of total CPU. The meters are sampled all the time, so the history is ready when someone opens the page.
- The process I/O rate uses its own `dt` (`_proc_t`), counted from the previous process collection. This keeps the rate correct even after a gap with no clients.
- The process list sorts by **Memory** by default, because the user asked for it.
- **Avg CPU** is the average over the last 60 s. It is computed from each process's cumulative `cpu_times()` (kept in `_proc_cpu`), not by averaging samples, so it stays correct across gaps with no clients. The table uses `table-layout: fixed` with widths set in `<colgroup>`, so the columns don't jump between ticks. The user asked for this. Keep it that way if you add columns.
- **Grouping by name** (the user asked for this): the table shows one row per process name. Groups with more than one process can be expanded to show each process. The server tracks each group's cumulative CPU time (`_group_totals`). That total includes members that have exited, so a crash loop with a new PID every second (for example an app that keeps restarting because an old instance holds its port) still gets a stable Avg CPU. A group with no live process stays as a dimmed "exited" row while its average is ≥ 0.1 %. Limitation: CPU a process uses after its last sample and before it exits is lost, so short-lived loops are under-counted.
- **Network by container:** Linux has no per-process network counter. The user rejected the advanced options (packet capture or eBPF), so this panel shows each network namespace instead. `_container_net` reads `/proc/<pid>/net/dev` for one process per namespace and counts only `eth*`, because `tun0`/`wg0` would count VPN traffic twice. Names come from the cgroup's container id, looked up in `/var/lib/docker/containers/<id>/config.v2.json` (a read-only mount at `/host/docker-containers`). Containers that share a namespace are joined with `+`, for example `vpn + torrent`. A namespace that is not Docker is labeled by its systemd unit and owner, for example rootless Docker's rootlesskit appears as `docker.service (<user>)`. The namespace list is rescanned every 10 s. The panel always samples, without needing clients. It is sorted by the 60 s average and shows the top 6, with a "Show all" button. The host's own namespace is not in the panel; it is what the NIC meters show. The NIC can therefore show much more than the containers add up to, because processes on the host network are not in the panel.
- **Filesystems panel** (like `duf`): `_filesystems` reads the host's mounts from `/proc/1/mounts`, not the container's own. It runs `statvfs` on `/proc/1/root/<mount>`, so no extra volume is needed. It lists block devices (not loop devices) and `fuse.*` mounts, and skips `/boot` and `/snap`. Bind mounts are reduced to one row per device. It is rescanned every 10 s. Use% is used/size, as in duf, and the bar colours follow duf's thresholds: yellow from 50 %, red from 90 %.
- **System panel:** it sits above the meters (the user asked for this). It has 12 tiles, and each one has an icon chip and a corner tint in the meter colour of its topic (`SYS_ICONS` and the colour token in `renderSystem`). The grid has 6, 4, 3 or 2 columns, so the last row is always full; keep the count divisible if you add tiles. Static facts are read once at startup (`_static_info`): OS from the host's `/proc/1/root/etc/os-release`, the board from `/sys/class/dmi`, and the disks from `/sys/block` (`rotational` decides HDD or SSD). IP, gateway and the container count are refreshed every 10 s. The container count comes from `State.Running` in `config.v2.json`, not from cgroups, because Kongo's own processes see their cgroup as `/` and would be missed. CPU temperature and frequency are live. The public IP is the only outbound call: `public_ip_loop` fetches `PUBLIC_IP_URL` (api.ipify.org) every 30 min, and an empty value turns it off.
- Users that show up as numbers (201, 999) are users inside other containers that have no entry in the host's passwd. This is expected.
- User decisions: the process list is **read-only** (no kill), on purpose. The UI is in English.
- Colours come from the dataviz reference palette, one hue per meter (the user wanted more colour): CPU blue, Memory violet, Disk Read aqua, Disk Write yellow, Network In orange, Network Out magenta. Light and dark mode each have their own token values: dark in `:root`, light in `:root[data-theme="light"]`. `data-theme` is always set by an inline script in `<head>`, before first paint: it uses the choice saved in localStorage (`kongo-theme`), or the system setting if none is saved. The sun/moon switch in the top bar saves the choice (the user asked for this). Charts read their colours from CSS, so they are redrawn when the theme changes. The look is soft on purpose (the user asked for it): rounded cards with shadows, an icon chip per meter, smoothed lines with a gradient fill.
- Fonts are Inter (UI) and Manrope (headings and values). They are bundled in `app/static/fonts/` as woff2, under SIL OFL, so the page has no external dependencies. `main.py` registers the `font/woff2` MIME type because python:3.12-slim has no `/etc/mime.types`.

## Build, run and verify

- The static files are **baked into the image** (`COPY app`). After any change, run `docker compose up -d --build` on the server (`CLAUDE.local.md` says how to reach it).
- Check the data: `curl -s localhost:8090/api/snapshot | head -c 1500` on the server. Compare the values with `free -b` and `top -bn2 -d1`.
- Check under load: `dd if=/dev/zero of=./ddtest bs=1M count=3000 oflag=direct`. Disk Write should rise on the disk you wrote to, and `dd` should appear in the process list with its write rate. Remove `ddtest` afterwards.
- Look at the page: `node tools/screenshot.mjs http://<host>:8090/ /tmp/desk.png 1400 1000`. Add `390 900 dark` for the mobile dark view. The README image `docs/screenshot.png` is taken with `KONGO_ANON=1 … docs/screenshot.png 1400 1212 dark`, which replaces the host name, IPs and MAC with made-up values. Always use it for images that get committed. This uses local Chromium over CDP. Do not use plain `chromium --screenshot`, because it captures before the WebSocket data arrives.
