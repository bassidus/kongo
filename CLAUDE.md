# Kongo

A web page that shows live stats for a Linux server, in the style of Windows Task Manager. It has six meters (CPU, Memory, Disk Read, Disk Write, Network In, Network Out), each with a 60 s history graph and the current value, plus panels for the system, filesystems and network by container, and a sortable process list. It runs as one Docker container on port **8090**.

## Working environment

- **The repo is public.** Details about the user's own server (host name, paths, users, hardware, the services it runs, how to reach it) belong in `CLAUDE.local.md`, which is not committed. Never put them in tracked files, comments or commit messages. Use generic examples instead.
- Local settings such as `TZ` go in `.env` next to `docker-compose.yml`, which is not committed either.

## Architecture

- `app/main.py` is FastAPI + psutil. A `Sampler` loop samples once a second. It computes rates from counter deltas and keeps a 60-point history in a `deque`. It pushes JSON to every client over the WebSocket `/ws`: an `init` message with the history on connect, then a `tick` message each second. `GET /api/snapshot` is for debugging and takes about 2 s, because it waits for two ticks so that the process CPU and IO deltas are valid.
- `app/static/` has `index.html`, `style.css` and `app.js`, with no external dependencies. The graphs are drawn by hand on `<canvas>` (the `Chart` class in `app.js`). The process table re-renders `tbody` on every tick. Sorting, filtering and the selected row are kept in the `table` object.
- `docker-compose.yml` runs the container with `network_mode: host` and `pid: host`, so it sees the real NIC counters and every host process. It adds `cap_add: SYS_PTRACE` and `apparmor:unconfined` so it can read `/proc/<pid>/io`, and it mounts `/etc/passwd` and `/etc/group` read-only to resolve user names. It also mounts `/var/lib/docker/containers` read-only to look up container names.

## Decisions and gotchas

- **Disk:** only whole disks are summed (`DISK_RE`: `sdX`, `nvmeXnY`, …). Partitions and loop devices would double count.
- **Network:** only physical NICs are counted, meaning those with `/sys/class/net/<if>/device`. Docker bridges and veth interfaces would double count. The env var `NET_IFACES` overrides this.
- **CPU:** psutil does not count iowait as busy, which matches Task Manager. On servers with busy HDDs iowait can be high, so `top` shows a lot of `wa` that is not part of the CPU value. A process's CPU % is normalized against all cores, so the processes add up to the total.
- Processes are only collected while a client is connected (`with_procs`). This costs about 2 % of total CPU. The meters are sampled all the time, so the history is ready when someone opens the page.
- The process I/O rate uses its own `dt` (`_proc_t`), counted from the previous process collection. This keeps the rate correct even after a gap with no clients.
- The process list sorts by **Memory** by default, because the user asked for it.
- **Avg CPU** is the average over the last 60 s. It is computed from each process's cumulative `cpu_times()` (kept in `_proc_cpu`), not by averaging samples, so it stays correct across gaps with no clients. The table uses `table-layout: fixed` with widths set in `<colgroup>`, so the columns don't jump between ticks. The user asked for this. Keep it that way if you add columns.
- **Grouping by name** (the user asked for this): the table shows one row per process name. Groups with more than one process can be expanded to show each process. The server tracks each group's cumulative CPU time (`_group_totals`). That total includes members that have exited, so a crash loop with a new PID every second (for example an app that keeps restarting because an old instance holds its port) still gets a stable Avg CPU. A group with no live process stays as a dimmed "exited" row while its average is ≥ 0.1 %. Limitation: CPU a process uses after its last sample and before it exits is lost, so short-lived loops are under-counted.
- **Network by container:** Linux has no per-process network counter. The user rejected the advanced options (packet capture or eBPF), so this panel shows each network namespace instead. `_container_net` reads `/proc/<pid>/net/dev` for one process per namespace and counts only `eth*`, because `tun0`/`wg0` would count VPN traffic twice. Names come from the cgroup's container id, looked up in `/var/lib/docker/containers/<id>/config.v2.json` (a read-only mount at `/host/docker-containers`). Containers that share a namespace are joined with `+`, for example `vpn + torrent`. A namespace that is not Docker is labeled by its systemd unit and owner, for example rootless Docker's rootlesskit appears as `docker.service (<user>)`. The namespace list is rescanned every 10 s. The panel always samples, without needing clients. It is sorted by the 60 s average and shows the top 6, with a "Show all" button. The host's own namespace is not in the panel; it is what the NIC meters show. The NIC can therefore show much more than the containers add up to, because processes on the host network are not in the panel.
- **Filesystems panel** (like `duf`): `_filesystems` reads the host's mounts from `/proc/1/mounts`, not the container's own. It runs `statvfs` on `/proc/1/root/<mount>`, so no extra volume is needed. It lists block devices (not loop devices) and `fuse.*` mounts, and skips `/boot` and `/snap`. Bind mounts are reduced to one row per device. It is rescanned every 10 s. Use% is used/size, as in duf, and the bar colours follow duf's thresholds: yellow from 50 %, red from 90 %.
- **System panel:** it sits above the meters (the user asked for this). It has 12 tiles, and each one has an icon chip and a corner tint in the meter colour of its topic (`SYS_ICONS` and the colour token in `renderSystem`). The grid has 6, 4, 3 or 2 columns, so the last row is always full; keep the count divisible if you add tiles. Static facts are read once at startup (`_static_info`): OS from the host's `/proc/1/root/etc/os-release`, the board from `/sys/class/dmi`, and the disks from `/sys/block` (`rotational` decides HDD or SSD). IP, gateway and the container count are refreshed every 10 s. The container count comes from `State.Running` in `config.v2.json`, not from cgroups, because Kongo's own processes see their cgroup as `/` and would be missed. CPU temperature and frequency are live. The public IP is the only outbound call: `public_ip_loop` fetches `PUBLIC_IP_URL` (api.ipify.org) every 30 min, and an empty value turns it off.
- **Package updates** (the user asked for this, for any package manager): a badge after the host name shows the number of available updates (red if any are security updates), and clicking it opens a `<dialog>` with the list. The logic is in `app/updates.py`: one `Manager` per package manager (apt, dnf5, dnf4, zypper, pacman, apk). `detect` picks the first whose binary exists in the host's root; with none, the badge stays hidden. The check runs the host's own binary with `chroot --userspec=65534:65534 /proc/1/root`, so it runs as nobody and can't change anything. It needs no extra volume and gives exactly what the host's package manager shows, including third-party repos. Each run gets a temporary HOME in the host's `/tmp` (`scratch_home`, owned by the user the run is as), deleted afterwards (dnf5 writes its log there; dnf5 also needs `--setopt=system_cachedir` to read the system cache as non-root). `updates_loop` in `main.py` reruns when the newest mtime of the manager's `installed` or `lists` globs or of `/run/reboot-required` changes (polled every 60 s), and at least every `recheck` (1 h). **Refreshing the lists** (the user asked for every 12 h): when `lists_updated` (newest mtime of the `lists` globs, or the last refresh by Kongo, because a refresh that finds nothing new may touch no file) is older than `UPDATES_REFRESH_HOURS` (default 12, 0 = off and Kongo only reads), the loop runs the manager's `update` **as root** in the chroot: `apt-get update`, `dnf makecache`, `zypper refresh` or `apk update`, as the host's own timers do. If those keep the lists fresh, Kongo never refreshes. A failed refresh (offline, lock held) is logged and retried in 10 min, and the check still runs on the old lists. **Opening the popup** (the user asked for this, so that a restart doesn't miss new updates) calls `POST /api/updates/check`. That adds a future to `updates_waiters` and wakes the loop. The loop refreshes the lists if they are older than `UPDATES_ON_OPEN` (10 min), checks again, and resolves every waiting future, so two tabs share one `apt-get update`. The reply is the fresh list. Meanwhile the popup shows the current list with "checking for new updates…", and Restart and Install are disabled. `loadSeq` keeps a slower, older reply from overwriting the newer one. The endpoint has no password: the worst it can do is an `apt-get update` every 10 min. After a failed check it retries in 10 min and logs the error to `docker logs`. **pacman** never syncs the host's own sync dbs (partial upgrades): `update_pacman` does what `checkupdates` does and syncs a private copy in `/var/cache/kongo/pacman` on the host (seeded from the host's dbs, `local` symlinked; `pacman -Sy` refuses to run as non-root, so that step runs as root). `check_pacman` reads that copy once it exists. Do not move it to `/tmp`: pacman writes there as root, and a local user could plant symlinks in a world-writable directory. Security updates are marked for apt (suite `*-security`) and dnf (a second run with `--security`); zypper's are patches, not package flags, so they are not marked. Restart required comes from `/run/reboot-required` (Debian/Ubuntu, with `.pkgs`), from the running kernel's directory missing under `/usr/lib/modules` (Arch and others remove the old one), from a `/boot/vmlinuz-*` or `/usr/lib/modules/*/vmlinuz` whose **ctime** is after the boot (a kernel installed since then; not mtime, because packages keep their build date as mtime; this caught a real case where Ubuntu's `/run/reboot-required` was missing), and from `zypper needs-rebooting` (exit 102). The tick carries only a summary (`count`, `security`, `reboot`); the dialog fetches the list, the manager name and the upgrade command from `GET /api/updates`. With 0 updates but a restart needed, the badge says "Restart required". On phones the dialog shows one card per package instead of four columns. To test another distro without a VM, start its image as a container on the server, and call `updates.refresh(root, mgr)` and then `updates.check(root, mgr, time.time())` with `root = f"/proc/{pid}/root"` and `mgr = updates.detect(root)` inside the kongo container (pid: host, so its root is reachable). Ubuntu, Fedora 41 (dnf5), Rocky 9 (dnf4), Leap, Tumbleweed, Arch and Alpine were all checked this way against the native command's counts, both reading and refreshing.
- **Container updates** (the user asked for this): `app/images.py`. It talks to the host's Docker API over `/proc/1/root/run/docker.sock` (not `/var/run/…`: `/var/run` is an absolute symlink and would resolve inside the container), so no volume is needed. For each running container it compares the digests in the image's `RepoDigests` with the digest the registry gives for the tag (a `HEAD` on `/v2/<repo>/manifests/<tag>` with an anonymous Bearer token from the 401's `WWW-Authenticate`; Docker Hub doesn't count `HEAD` against the pull limit). `parse_ref` maps `nginx` to `registry-1.docker.io/library/nginx`. Each container gets one status: `pull` (the registry has a newer image), `recreate` (the tag's local image ≠ the container's `ImageID`, so a newer image is already pulled), `ok`, `local` (no RepoDigests: built here), `pinned` (`@sha256`) or `error`. When the tag has moved on, Docker shows the image id as the container's `Image`, so the name comes from `Config.Image`. Registry answers are cached per ref for `CONTAINER_UPDATES_HOURS` (default 12; the user said 12 h is enough, so opening a popup does **not** ask the registries again). The local side is checked every minute by `images_loop`, so a container that was updated drops off within a minute. The tick's `updates` summary has `containers` (pull + recreate) and `images`. The badge counts them, and the updates popup has a "Docker containers" section with only those that need something. **The Docker tile is clickable** (the user asked for this) and opens `#docker-dialog` with every running container from `GET /api/containers`, updates first, and its sub line says how many updates there are. **Updating containers** (the user asked for this): in the Docker popup, every updatable row has an **Update** button (`data-update`, sets `adminTarget`), and the footer has **Update all** (`adminTarget = null`, so it sends all of `dockerPending`). Both are behind the same password (`POST /api/admin/containers` with the `names`, so only containers the popup showed get recreated). It runs as the same `kongo-upgrade` unit as Install updates (one job at a time; `job()["kind"]` comes from the unit's Description), so the job view, log and busy handling are shared. `images.update_script` writes a script to `/var/cache/kongo/update-containers.sh` (root-only; a file rather than `sh -c`, so systemd-run doesn't expand its `$`, and `shlex.quote` handles the folders). Per project, it runs `cd <working_dir> && docker compose -p … -f <config_files> pull <services> && … up -d`: `up -d` for the whole project, as the hint says, so compose recreates only the changed containers and their dependents (for example an app on a VPN container's network). Only compose containers are `updatable` (they have the `project`/`dir`/`service` labels); `docker run` ones are counted in the hint as "update by hand". While the job runs, `images_loop` waits (5 s polls) and checks as soon as it ends; the endpoint sets `images_wake`. The password form (`#admin-form`) and the job's log (`#job`) are shared by both popups: `mountAdmin(dlg)` moves them into the open one (`.job-slot`, `.dialog-foot`), and `renderJob` works on `activeDlg`. To test it, use a throwaway compose project with an old image tagged `:latest`: call `images.update_script` and `admin.start_containers` from python in the container, then `compose down` and remove it. Never use a real stack. To test the check, tag an old image as `:latest` and run a container from it (status `pull`), then pull the real `:latest` (status `recreate`), and clean up afterwards.
- Users that show up as numbers (201, 999) are users inside other containers that have no entry in the host's passwd. This is expected.
- **Install updates / Restart** (the user asked for this, with their own Linux password, "it is only meant to run locally"): `app/admin.py`. `ADMIN_ACTIONS` (code default off, `on` in `docker-compose.yml`) plus `/run/systemd/system` on the host turn on two buttons in the updates popup. Each one asks for a user name and password. `admin.admin_users()` (a usable hash and an admin) goes out as `admin_users` in `/api/updates` (the user asked for this). With one user, the popup asks only for the password, for example "Restart the server as alice". With several, it has a `<select>` of them, and the last choice is remembered in localStorage (`kongo-admin-user`). With none, `actions` is false and there are no buttons. To try several users without adding any on the host, stage it in the screenshot tool: `KONGO_CLICK='#updates|js:adminUsers = ["alice", "bob"]|[data-action=restart]'`. `verify` checks them against the host's `/etc/shadow` with the container's `libcrypt.so.1` via ctypes (yescrypt and sha512; Python's `crypt` module is gone in 3.13). The user must be root or in `sudo`/`wheel`/`admin` in the host's `/etc/group`. An unknown user is hashed anyway, so it takes as long. `Guard` locks out every client for 15 min after 5 failures in 15 min (in memory, so a restart clears it). Credentials go with each POST (`/api/admin/upgrade`, `/api/admin/restart`); there is no session, so there is nothing for CSRF. **Both actions run as transient systemd units on the host** (`systemd-run` in the chroot), never inside the container: the update list includes docker-ce/containerd, and upgrading those restarts Docker, which would kill an apt running in the container mid-dpkg. The upgrade is the unit `kongo-upgrade` with `RemainAfterExit=yes`, so its result and its log (`journalctl _SYSTEMD_INVOCATION_ID=…`) can still be read after it ends and after Kongo restarts. The next run first does `stop` and `reset-failed` on it. The command is `Manager.install` in `updates.py`: it runs under `/bin/sh -c`, with `DEBIAN_FRONTEND=noninteractive` and `NEEDRESTART_MODE=l` (services are not restarted; that is the Restart button's job). apt refreshes the lists first, keeps changed conffiles and waits for the dpkg lock. **No `$` in those commands**: systemd-run expands it. Restart runs `systemd-run --on-active=3 systemctl reboot`, so the HTTP reply gets out first. After a confirmed Restart, the popup shows only the restart's progress (`restart-mode`, `startRestartView`) and **can't be closed until the server is back** (the user asked for this). The Close button is hidden, a backdrop click and Esc (`cancel`) are refused, and if the browser closes it anyway, the `close` handler opens it again. "Back" means a tick whose `host.uptime` is shorter than the time since the click (`restartTick`), not just a WebSocket that reconnected. The popup then says "The server has restarted and is back" and checks for updates. After 10 min without that, it warns and can be closed. To test it without a reboot: `KONGO_CLICK='#updates|js:startRestartView()|js:restartTick({uptime: 0})'`. `GET /api/admin/job` (no password; it shows the same packages the page already lists) returns the state and the last 400 log lines. From the Install click until "Back to the list", the popup shows only the run's output (`jobView`, class `job-mode`: the list and the Install button are hidden; the user asked for this). It also does this when it is opened while a run is going. It polls every 2 s while a job runs, and keeps polling while Kongo is down. While a run is going, `updates_loop` doesn't check at all (dpkg is half done; that is what showed a stale 23-of-46 list after a real run) and polls `admin.status()` every 5 s. The run's end time is part of the loop's `state`, so every finished run is followed by a recheck, even one that changed no package. `/api/admin/upgrade` sets `updates_wake`, so the loop sees the run at once and does not wait up to 60 s. In the list view, Install is disabled when there is nothing to install, and both buttons are disabled until the list's `checked` is later than the run's end. Test the job machinery with a simulated command, for example `admin.start_upgrade("apt-get -s upgrade")`, and then `systemctl stop kongo-upgrade; systemctl reset-failed kongo-upgrade`. Never test with the real buttons on the user's server.
- User decisions: the process list is **read-only** (no kill), on purpose; Install updates/Restart above are the only actions. The UI is in English.
- Colours come from the dataviz reference palette, one hue per meter (the user wanted more colour): CPU blue, Memory violet, Disk Read aqua, Disk Write yellow, Network In orange, Network Out magenta. Light and dark mode each have their own token values: dark in `:root`, light in `:root[data-theme="light"]`. `data-theme` is always set by an inline script in `<head>`, before first paint: it uses the choice saved in localStorage (`kongo-theme`), or the system setting if none is saved. The sun/moon switch in the top bar saves the choice (the user asked for this). Charts read their colours from CSS, so they are redrawn when the theme changes. The look is soft on purpose (the user asked for it): rounded cards with shadows, an icon chip per meter, smoothed lines with a gradient fill.
- Fonts are Inter (UI) and Manrope (headings and values). They are bundled in `app/static/fonts/` as woff2, under SIL OFL, so the page has no external dependencies. `main.py` registers the `font/woff2` MIME type because python:3.12-slim has no `/etc/mime.types`.

## Build, run and verify

- The static files are **baked into the image** (`COPY app`). After any change, run `docker compose up -d --build` on the server (`CLAUDE.local.md` says how to reach it).
- Check the data: `curl -s localhost:8090/api/snapshot | head -c 1500` on the server. Compare the values with `free -b` and `top -bn2 -d1`.
- Check under load: `dd if=/dev/zero of=./ddtest bs=1M count=3000 oflag=direct`. Disk Write should rise on the disk you wrote to, and `dd` should appear in the process list with its write rate. Remove `ddtest` afterwards.
- Look at the page: `node tools/screenshot.mjs http://<host>:8090/ /tmp/desk.png 1400 1000`. Add `390 900 dark` for the mobile dark view. The README image `docs/screenshot.png` is taken with `KONGO_ANON=1 … docs/screenshot.png 1400 1212 dark`, which replaces the host name, IPs and MAC with made-up values. Always use it for images that get committed. `KONGO_CLICK=<selector>` clicks an element before the capture, for example `KONGO_CLICK=#updates` for the updates dialog. This uses local Chromium over CDP. Do not use plain `chromium --screenshot`, because it captures before the WebSocket data arrives.
